2) Best design pattern recommendation
✅ State Pattern (for AI decision state / intent lifecycle)
3) Why it fits this project
Your architecture already uses a tick-based loop and “Brain decides intent each tick,” which naturally maps to explicit AI states (e.g., Scavenge, Engage, Flee, Trade, Recover) with controlled transitions. 

WSSTwo.tsx shows complex conditional decision logic per brain type; State helps reduce branching complexity by moving transition rules into modular state classes/objects while preserving behavior. 

It aligns with your roadmap and ADRs because it improves internal organization, not architecture direction (still fixed timestep, still Sense→Decide→Act, still Brain interface concept). {line_range_start=53 line_range_end=60 path=wss(full game ideas)/ROADMAP.md git_url="https://github.com/CaseyWongWc/testing/blob/wss2/wss(full game ideas)/ROADMAP.md#L53-L60"}

4) Where it should be applied
Apply first to brain decision lifecycle, not to rendering/combat/map generation:

Primary target: decision code currently centralized in calculateBrainMoveByType(...) in WSSTwo.tsx. 

Model mapping: map existing intents/behaviors into states that can transition by resource pressure, threat, progress, and visibility.

Phase-aligned path: start in the current phase component layer (src/combat) as an internal refactor, then migrate the same state objects into future src/wss2/ modules later (matches ADR-001 intent). 

5) Minimal integration plan (no full redesign)
Define a tiny AIState interface (e.g., name, evaluateTransition(ctx), chooseAction(ctx)).

Create 3–4 initial states only (ex: AdvanceEast, Resupply, Trade, Recover) based on existing heuristics.

Wrap existing branching logic into those states incrementally (no behavior tuning yet).

Keep existing BrainType selection intact; each brain can prefer different transition thresholds/weights.

Add a transition trace string to preserve current reasoning UI output.

Roll out in one scene first (WSSTwo), then optionally phase components (WSSPhase1/2/3) after parity checks.

This keeps systems intact and follows roadmap constraints by limiting scope to AI decision orchestration.

6) Optional alternatives
Behavior Tree (BT): very expressive for complex AI, but heavier than needed right now for your current phase and “minimal change” requirement.

Utility AI: great for tunable scoring-based choices; good later for advanced AI phases, but can be overkill before state modularization.

Command Pattern for intents: useful adjunct pattern (for queued/resolved actions per tick), but less directly impactful today than State for decision complexity.
