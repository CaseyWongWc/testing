## v0.1 (first playable slice) — scope lock

**Goal:** Run a simulation where **multiple survivor AIs** move, scavenge, and fight **real-time** enemies on a grid, with a clear **lose condition** and a basic **progression trigger**.

### Non‑negotiables (5)

1. **Grid world + terrain costs** (walkable vs blocked, optional terrain movement cost)
2. **Real-time tick loop** (update at fixed timestep)
3. **Survivor squad (2–4 AI agents)** with simple roles/brains (balanced, cautious, aggressive)
4. **Zombie enemies + spawners** (simple rift with cooldown + cap)
5. **Win/Lose:** lose when all survivors dead. Win = survive X seconds **or** reach an extraction tile (keep it simple for v0.1)

### Explicitly *not* in v0.1 (to protect scope)

- Vehicles
- Multi-floor buildings
- Trading / Survivor Market
- Hostile human NPCs
- Weather
- Sound propagation
- Boss arenas

---

## Core loop (real-time)

At each **tick** (e.g. 20–60 ticks/sec):

- Sense: each agent gathers local info (nearby enemies, loot, exits)
- Decide: brain picks an **intent** (move, attack, loot, flee)
- Act: movement + attacks resolve
- Spawn: spawners generate enemies if allowed
- Cleanup: remove dead entities, drop loot

**Definition of “done” for v0.1:**

- You can start a run, watch it play, and it ends in a win/lose without manual intervention.

---

## Minimum object model (OOP)

Keep it small and extendable.

### World & map

- `Game`
    - owns main loop, tick timing, run state
- `World`
    - holds `GridMap`, entity lists, spawners, global parameters
- `GridMap`
    - tiles, bounds, helper queries
- `Tile`
    - terrain type, walkable, movementCost, maybe coverValue (future)

### Entities

- `Entity` (base)
    - id, position, alive, update(world)
- `Actor` extends `Entity`
    - health, speed, faction, sensors, canMove/canAttack
- `Survivor` extends `Actor`
    - inventory, weapon, brain
- `Zombie` extends `Actor`
    - simple brain (seek nearest survivor)

### AI

- `Brain` (interface)
    - `decide(actor, world) -> Intent`
- `Intent` (data)
    - type: Move/Attack/Loot/Flee/Idle
    - targetPos or targetEntityId

### Combat

- `Weapon`
    - damage, range, cooldown, ammo(optional in v0.1)
- `CombatSystem`
    - resolves hits, cooldowns, death

### Items (v0.1 minimal)

- `Item` extends `Entity` (or simple struct list)
    - type: HealthPack, Ammo (optional)
- `PickupSystem`
    - handles pickup + apply effects

### Spawning

- `Spawner` extends `Entity`
    - spawnCooldown, maxAliveFromThisSpawner, spawnType

### Pathing

- `Pathfinder`
    - A* or weighted BFS over `GridMap`
    - survivors use for movement intents

## Maze idea #2: Central “frame maze” safe hub (spawn ring)

**Classification:** Map Generation + Level Structure (a persistent *hub geometry*), not a biome.

### Concept

- A **rectangular frame maze** sits at the **center** of the map.
- Inside the ring:
    - Survivor spawn area
    - The Portal
- The frame acts like a semi-thin labyrinth wall layer around the hub.
- Portal starts as an **inactive floor tile** in the hub.
    - Survivors can **walk over it anytime**.
    - It only triggers evacuation after it becomes **ACTIVE** (unlocked/activated by objectives).
    - Survivors **spawn neatly arranged on top of/around the inactive portal** each new map (overflow may briefly clip if the survivor count is absurd).
- Toggle: `center_frame_enabled` (if off, do normal center spawn without ring).

### Why this is good

- Gives every level an instantly recognizable **anchor**.
- Naturally supports your loop:
    - objectives out in the world → return to center → portal evac
- Works great with fog-of-war and enemy “last seen” markers.

### Design risks (and how to control them)

- Risk: Survivors can camp forever in the ring.
    - Control: portal is **locked** until objectives complete.
    - Control: spawners or onslaught pressure can eventually push inward (later).
- Risk: Pathing bottlenecks.
    - Control: add **2–4 gates** (openings) in the frame.

### Minimal v0.1 implementation (simple geometry)

You do **not** need a full maze algorithm here at first.

1. Pick a hub size, e.g. `hub_inner_w = 8`, `hub_inner_h = 8`.
2. Pick a frame thickness: `frame_thickness = 2` tiles.
3. Carve a rectangle ring (walls) around the hub.
4. Add `gate_count = 2` openings on opposite sides.
5. Place survivors + portal in the hub center.

### v0.2 upgrade (make it a real “frame maze”)

Once the base ring works:

- Run a maze algorithm *only inside the frame band* (the donut/ring area), then thicken corridors.
- Keep hub interior open for readability.

### Suggested parameters

- `center_frame_enabled`: true/false
- `frame_thickness_tiles`: 2
- `gate_count`: 2 or 4
- `hub_inner_size`: 8×8 (tune later)

### “Labyrinth” biome (optional)

You *could* add a unique biome called **Labyrinth**, but you’re right that it may not blend naturally with other outdoor biomes.

If you keep it, I’d treat it as a **special map type** (like a dungeon level) rather than a normal biome roll.

- Entry via: portal transition, boss arena trigger, or rare objective chain.

### Hallway width (not 1-tile thick)

Great idea for readability and movement.

- Represent corridors as **2–3 tiles wide**.
- Easiest way: generate a 1-tile maze skeleton, then **“thicken”** corridors by expanding carved cells to neighboring tiles.

### Floors as material groups (instead of “biome floors”)

Also good. You can decouple **tile function** from **tile cosmetic skin**.

- Functional terrain: `walkable`, `movementCost`, `blocksVision?`
- Cosmetic skin: concrete, cracked stone, grass, mossy-clean variants
- Weather + time of day still apply as global modifiers.

### Recommendation

Keep Labyrinth as a **rare/special level** in Phase 2/3.

For v0.1, get value by using **maze pockets inside buildings/caves** first.

## Fog of war + Vision (radius-based) — spec (WSS2)

Your direction is consistent and will feel more natural than “tile pattern” vision.

### Vision model

- Each survivor has a **vision radius** `vision_r` (in tiles).
- A tile is visible if `distance(tile, survivorPos) <= vision_r`.
- Use Euclidean distance for a true circle, or Chebyshev for a square/diamond. **Recommendation:** Euclidean for the feel you want.

### Memory (explored map)

- Fog of war is **remembered**.
- Maintain per-survivor (or shared team) arrays:
    - `seen[y][x]` (has ever been seen)
    - `visible[y][x]` (currently visible this tick)
- Rendering idea:
    - `visible` = full brightness
    - `seen && !visible` = dimmed/gray
    - `!seen` = hidden

### Shared team fog (chosen)

- The fog-of-war memory is **shared across the survivor team**.
- Use a single set of arrays for the whole run:
    - `team_seen[y][x]`
    - `team_visible[y][x]` (recomputed each tick from all living survivors)

**Update rule (each tick)**

1. Clear `team_visible` to false
2. For each living survivor:
    - Compute tiles within `effective_vision`
    - Mark those tiles as `team_visible = true`
    - Also set `team_seen = true`

### “Last seen enemy” markers (red pings)

### Marker persistence rule (chosen)

- Markers (red outline / red ping) persist **until you look that way again**.
    - Meaning: the marker stays while the tile is in **historical fog** (`team_seen && !team_visible`).
    - When the tile becomes **currently visible** again, remove the marker (or update it to the enemy’s current position if the enemy is actually visible).

### Two-step fog rendering (chosen)

- **Immediate / visible:** normal color (`team_visible = true`)
- **Historical / remembered:** dulled/washed (`team_seen = true && team_visible = false`)
- **Unknown:** hidden (`team_seen = false`)

### Horror variant: “phantom marker” / scripted sighting

You want the option for a boss (or special enemy) to appear as a marker once and linger even before anyone truly sees it.

Implement as a separate marker type so it does not conflict with real tracking:

- `PhantomMarker`
    - `pos`
    - `type` (BOSS_HINT, SCREAMER_HINT, etc.)
    - `created_tick`
    - `clear_rule`: UNTIL_TILE_VISIBLE (matches your preference)

**Rule:** phantom markers render on historical fog, and clear when the tile becomes visible.

### Day/night effect (multiplier)

- Define a multiplier `vision_mult` applied to base vision.
- Night vision radius: **60–80%** of daytime.
    - Example: `vision_mult_day = 1.0`, `vision_mult_night = 0.7`.

### Traits & status modifiers

Vision can be modified by traits and temporary states.

- Trait example: `Scout` doubles base vision.
- Status examples:
    - `Downed` reduces vision
    - `WellFed` increases vision

**Simple formula**

`effective_vision = base_vision * trait_mult * status_mult * timeOfDay_mult`

### Vision bypass tools

- **Night vision goggles**: override night multiplier (or add a flat bonus).
- **Weapon range > vision**: allow firing at targets outside vision if they are:
    - previously seen in memory, OR
    - revealed by teammate vision, OR
    - revealed by a “ping” mechanic (future)

### Implementation notes (performance)

- Only recompute `visible` for tiles in the bounding box of the radius each tick.
- If you end up with 1–5 survivors, this is cheap even at 60 ticks/sec.

### One clarifying decision (keeps code clean)

For **Activate Switch** and other interactions, should a survivor need to:

- **Tap once** (instant completion)?

✅ **Decision: Hold-to-activate switch**

- Interaction takes **N ticks**.
- While activating, the survivor is **soft-locked** in place.
- A **circular progress indicator** fills up (white, transparent).
- If the survivor is user-controlled, they can **cancel** by moving.

### Minimal interaction state machine

Add a tiny state machine per survivor (or per interactable):

- `IDLE`
- `ACTIVATING` (has `activate_target_id`, `activate_progress_ticks`)

**Rules**

- Enter `ACTIVATING` when a survivor is on the switch tile and decides to interact.
- Each tick in `ACTIVATING`: progress += 1.
- Cancel conditions:
    - Survivor moves (user input) → cancel
    - Survivor is forced to move (knockback later) → cancel
    - Switch tile no longer occupied → cancel
- Complete when `progress >= N`:
    - Mark objective complete
    - Fire event `SwitchActivated` (useful for objective manager)

### Suggested v0.1 parameters

- `switch_activate_ticks`: 60 (at 60 ticks/sec = 1 second) or 120 (2 seconds)
- `switch_cancel_on_damage`: false for v0.1 (add later if desired)
- `tick_rate`: 60 ticks/sec (so 60 ticks = **1 second**)
- `switch_activate_ticks`: **60** (1 second)

### AI behavior during activation (locked)

- AI survivors **do not auto-cancel** activation if enemies approach.
- Once an AI survivor starts activating, it stays soft-locked until completion (or a forced-move mechanic is introduced later).
